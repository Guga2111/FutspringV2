# Observability stack (VPS)

Prometheus, Grafana, node-exporter, cAdvisor and the logs (Loki + Alloy), shared by every project on the VPS, with
alerts sent to Telegram. Today only Futspring is
scraped. Deployed by `.github/workflows/deploy-observability.yml` (push to `main` touching `ops/observability/**`,
or run it by hand) to `~/observability` on the VPS; independent from the API deploy.

| Container | Image | Host port | `mem_limit` | Notes |
|-----------|-------|-----------|-------------|-------|
| prometheus | `prom/prometheus:v3.15.1` | none | 512m | scrape 30 s, retention 15 days / 2 GB, volume `prometheus_data` |
| grafana | `grafana/grafana-oss:13.0.2` | `127.0.0.1:8088` | 384m | login only (no sign-up, no anonymous), volume `grafana_data` |
| node-exporter | `prom/node-exporter:v1.12.1` | none | 64m | host `/proc`, `/sys`, `/` read-only |
| cadvisor | `ghcr.io/google/cadvisor:v0.60.6` | none | 256m | Docker containers only, housekeeping 30 s, heavy metrics off (disk usage included: it walks every container's files) |
| loki | `grafana/loki:3.7.9` | none | 384m | single binary on disk, retention 14 days, volume `loki_data` (~80 MiB idle) |
| alloy | `grafana/alloy:v1.21.3` | none | 192m | tails every container's stdout/stderr through docker-proxy, pushes to Loki; read positions in volume `alloy_data` (~100 MiB idle) |
| docker-proxy | `tecnativa/docker-socket-proxy:v0.5.0` | none | 64m | the only container of the logs with the Docker socket; GET `/containers/**` and `/networks` only, on an internal network with Alloy |

Prometheus and Loki are never exposed. Grafana is only reachable through nginx at `https://grafana.luisgosampaio.com`.

## Files

```
docker-compose.yml                      the seven containers, on the external "observability" network (docker-proxy on its own internal one)
prometheus/prometheus.yml               scrape jobs
loki/loki.yml                           Loki: filesystem storage, tsdb v13, retention 336h (compactor)
alloy/config.alloy                      Docker discovery → labels → level from the JSON → Loki
grafana/provisioning/datasources/       Prometheus (uid "prometheus") and Loki (uid "loki") datasources
grafana/provisioning/alerting/          contact-points.yml (Telegram), policies.yml (everything → Telegram), rules.yml (the alerts)
grafana/provisioning/dashboards/        dashboards.yml + json/: Futspring (ours), JVM (Micrometer) 4701,
                                        Node Exporter Full 1860, Cadvisor exporter 14282 (grafana.com, datasource
                                        references pointed at uid "prometheus")
.env.example                            GRAFANA_ADMIN_PASSWORD, GRAFANA_ROOT_URL, TELEGRAM_BOT_TOKEN
```

Dashboards are provisioned read-only: change the JSON here and redeploy. `futspring.json` was generated by a script;
edit it as JSON (or export a copy edited in Grafana and replace the file).

## Network and scraping

The stack creates no network: both deploys run `docker network create observability || true`. The API joins it
(`core/docker-compose.prod.yml`) and Prometheus scrapes `futspring-api:9091/actuator/prometheus`, the management port
inside the API container, which is never published on the host. The target uses the compose service name, not the
container name `futspring_api`: Tomcat answers 400 to a `Host` header with an underscore.

To add another project: attach its container to the `observability` network, expose its metrics on a port that isn't
published, and add a job to `prometheus/prometheus.yml`.

The workflow's smoke test requires Grafana's `/api/health`, every alert rule of `rules.yml` loaded, Loki's `/ready` and the stack's own targets (prometheus, node-exporter,
cadvisor). A project target that is down only warns, because on a push to `main` the API deploy runs at the same time.

## Logs (Loki)

Alloy discovers every container on the host (`discovery.docker`), reads its output (`loki.source.docker`) and pushes
it to `loki:3100`. Labels, all low cardinality:

| Label | From |
|-------|------|
| `service` | the compose service (`com.docker.compose.service`): `futspring-api`, `grafana`, `loki`… |
| `project` | the compose project: `futspring`, `observability` |
| `container` | the container name |
| `level` | `log.level` of a JSON line (the API logs ECS JSON); absent on plain lines |

Everything else stays in the line; read it with `| json` (dots become `_`). In Grafana → Explore → Loki:

```logql
{service="futspring-api", level="ERROR"}
{service="futspring-api"} | json | log_logger =~ ".*WebPushDispatcher"
sum by (level) (count_over_time({service="futspring-api"}[5m]))
```

**Why docker-proxy:** mounting `/var/run/docker.sock:ro` doesn't make the Docker API read-only (`:ro` only applies to
file operations on the socket), and whoever talks to the socket can start a privileged container. The proxy is the
only one with the socket and answers 403 to anything but `GET /containers/**` (list, inspect, logs) and
`GET /networks` (discovery reads them for its labels). cAdvisor still mounts `/var/run` for its own reasons.

Loki keeps 14 days (`retention_period`, applied by the compactor) and refuses lines older than 7 days. Its `/ready`
is part of the deploy's smoke test. Docker still keeps the last 30 MB per container (`json-file`), so
`docker logs` keeps working.

## Alerts (Telegram)

Grafana evaluates the rules of `grafana/provisioning/alerting/rules.yml` every minute (folder **Futspring**) and sends
every alert, and its resolution, to one Telegram chat. Provisioned rules, contact point and policy are read-only in
the UI: change the YAML and redeploy (the workflow restarts Grafana, which reads them only at start).

| Rule | Condition | For |
|------|-----------|-----|
| API fora | `up{job="futspring-api"} < 1` (no data counts as down) | 2 min |
| Erros 5xx | `outcome="SERVER_ERROR"` / all requests over 5 min > 1%, only with ≥ 0.2 req/s | 5 min |
| Pool do banco | `hikaricp_connections_pending > 0` | 5 min |
| Disco | used > 85% on any ext4 / xfs / btrfs filesystem of the host except `/boot` | 10 min |
| Memória da JVM | heap used / heap max > 90% | 10 min |
| Container reiniciando | `changes(container_start_time_seconds{name="futspring_api"}[15m]) > 0` | — |
| E-mail | `futspring_email_dropped_total` + `futspring_email_sent_total{result="failed"}` grew in 15 min | — |
| Web Push | `futspring_webpush_sent_total{result="failed"}` grew by more than 10 in 15 min | — |
| Sessões (Redis) | `futspring_session_refresh_total{result="error"}` + `futspring_session_open_total{result="error"}` grew in 5 min (Redis down: logins go out without a refresh cookie, refresh answers 503) | — |
| Erros do front | more than 20 `event=client_error` lines in 10 min (Loki) | — |

- A firing alert is repeated every 4 h (`policies.yml`); grouped by rule. A query that fails (Prometheus or Loki down)
  notifies as an error; a rule without data stays OK, except "API fora".
- **Container reiniciando ignores deploys:** `docker restart` (crash, `ExitOnOutOfMemoryError`) keeps the container
  id, so the same cAdvisor series changes; a deploy recreates the container, which starts a new series (another `id`
  label) and counts nothing. Checked only on the VPS (cAdvisor sees no containers on Docker Desktop / OrbStack):
  after a deploy, `changes(container_start_time_seconds{name="futspring_api"}[15m])` in Explore should be 0.
- **Silence** one (maintenance, a known issue): Alerting → Silences → New silence, matcher `alertname = Disco`.
- Annotations have no `$`: provisioning expands `$VARS` from the environment (it would eat `{{ $labels }}`).

**Creating the bot (once):**

1. In Telegram, talk to **@BotFather** → `/newbot`, pick a name and a username ending in `bot`. It answers the
   token (`123456789:AA…`) → GitHub secret `TELEGRAM_BOT_TOKEN`.
2. Send any message to the new bot (a bot can't start a conversation), or add it to a group and send one there.
3. Open `https://api.telegram.org/bot<TOKEN>/getUpdates` and copy `result[].message.chat.id` (a group's is negative,
   `-100…`) → GitHub secret `TELEGRAM_CHAT_ID`.
4. Run the workflow; then Alerting → Contact points → telegram → **Test** sends a message.

**Where each value goes:** the token reaches Grafana as an environment variable (`.env` → `TELEGRAM_BOT_TOKEN`). The
chat id is written by the workflow into `contact-points.yml` in place of `__TELEGRAM_CHAT_ID__`: Grafana re-reads an
expanded `$VAR` as YAML, so a numeric id becomes a number and the contact point is refused (quoting doesn't help).

## Grafana behind nginx (manual, once)

1. DNS: `A grafana.luisgosampaio.com → 31.97.169.38`.
2. `/etc/nginx/sites-available/grafana`:

   ```nginx
   server {
       server_name grafana.luisgosampaio.com;

       location / {
           proxy_pass http://127.0.0.1:8088;
           proxy_set_header Host $host;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
       }

       location /api/live/ {               # Grafana Live websocket
           proxy_pass http://127.0.0.1:8088;
           proxy_http_version 1.1;
           proxy_set_header Upgrade $http_upgrade;
           proxy_set_header Connection "upgrade";
           proxy_set_header Host $host;
       }
   }
   ```

3. `ln -s /etc/nginx/sites-available/grafana /etc/nginx/sites-enabled/grafana`,
   `nginx -t && systemctl reload nginx`, then `certbot --nginx -d grafana.luisgosampaio.com`.

## Local run

```bash
docker network create observability || true
GRAFANA_ADMIN_PASSWORD=local-pass TELEGRAM_BOT_TOKEN=<token> docker compose up -d   # Grafana on http://localhost:8088 (admin / local-pass)
```

Without a real bot, any `TELEGRAM_BOT_TOKEN` value starts Grafana (the sends just fail). To receive the alerts
locally, replace `__TELEGRAM_CHAT_ID__` in `contact-points.yml` with the chat id (don't commit it). Without the API,
"API fora" fires after 2 minutes.

For the API target, run the API container on the `observability` network with the alias `futspring-api`.
Logs of every local container show up in Explore → Loki after ~30 s (Alloy's discovery interval). The dev compose
logs plain text (`LOGGING_STRUCTURED_FORMAT_CONSOLE=""`), so its lines have no `level` label; drop that variable
to see the production JSON.
