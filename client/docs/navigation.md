# Navigation

> The pelada workspace (layout route, areas, subscription notice, chat) and the mobile shell below 768 px. Part of the [frontend guide](README.md).

## Rules

1. A new pelada area is a row in `PELADA_AREAS` (`utils/peladaAreas.ts`) plus a child route in `App.tsx`; areas are URL paths, never a query parameter.
2. `PeladaAreaSelect` (from md) and `PeladaAreaTabs` (below md) are the only area switchers; the sidebar has no pelada sub-navigation.
3. While the pelada isn't writable, sporting and finance writes are disabled with `aria-describedby` pointing at `#subscription-notice`; withdrawing, removing from a list and cancelling a session stay enabled.
4. Below md: titles and header buttons go through `useMobileHeader` / `MobileHeaderActions`, reloads through `useRefresh` (returning the promise), and every gesture has a one-tap alternative. From md nothing changes.

## Pelada navigation

- `/pelada/:id` is a nested **layout route** (`PeladaDetailPage`): it loads the pelada once (`usePeladaDetail` + `usePeladaActions`), owns the loading / access-denied / not-found states, the shared dialogs (invite, remove, stars, create session, `PlayerHistoryDialog`) and the chat, and renders the area pages through `<Suspense><Outlet context/></Suspense>`, so data, the header and the chat stay while switching areas. Area pages read it with `usePeladaWorkspace()`.
- **Subscription:** under the header of every area, `SubscriptionNotice` (`id="subscription-notice"`, from `pelada.subscription` and `utils/subscription.ts`): the creator sees "Teste grátis até 07/12" in the last 5 days of the trial (shown on time through `useNowUntil`), "Pagamento pendente: a pelada trava em 14/12" in the grace and "Pelada em somente leitura" when read-only or pending, each with an "Assinar" / "Renovar" link to the Assinatura area (`/pelada/:id/assinatura`, also from the session page; the notice is left out on the Assinatura area itself, which shows the state); members only see "Pelada em somente leitura: o criador precisa renovar a assinatura". While `writable` is false, every sporting and finance write is disabled with `aria-describedby` pointing at the notice: Nova sessão (header, overview, the ⌘K command left out), confirming attendance (`SelfConfirmButton readOnly`), the session page's actions and the finance writes. Withdrawing, removing someone from the list and cancelling a session stay enabled (the server allows them). The state comes with the response (no polling): a 402 that still happens shows the server's message in a toast.
- Every area page has `PeladaPageHeader`: a breadcrumb `Início > [pelada] > [área]` (`PeladaBreadcrumb` on shadcn `Breadcrumb`, literal `>` separators, the current page as plain text, the pelada name truncates first so nothing overflows at 375 px), the page h1 (the overview's h1 is in the banner) and `PeladaAreaSelect`: one shadcn `Select` with the groups "Pelada" (Visão geral, Membros, Sessões, Ranking, Prêmios) and "Gestão" (Financeiro, Convites, Configurações, Assinatura; Convites and Configurações admin-only, Assinatura creator-only, hidden from the others), navigating to the area's URL. The area's main action sits at the right of the title (`actions`, admins only): "Convidar jogador" on Membros, "Nova sessão" on Sessões. It is the only area switcher; the global sidebar has no pelada sub-navigation. On a page the caller can't open (an admin area opened by a member, Assinatura by anyone but the creator) the selector is hidden.
- Areas, labels, URL segments, groups and `access` (`member | admin | creator`, the lowest `PeladaRole` that sees it; `peladaRole(isAdmin, isCreator)`, creator ⊇ admin ⊇ member, shared as `role` / `isCreator` through `usePeladaWorkspace`; `canSeeArea`, `visibleAreas(role)`; `PRIMARY_PELADA_AREAS` defines the direct mobile destinations) come from `PELADA_AREAS` (`utils/peladaAreas.ts`); add a new area there and as a child route in `App.tsx`. URLs are paths (no query parameter for the area), so reload, back/forward and shared links open the same page. One area has a sub-path: `financeiro/{listId}` (a collection) is still the Financeiro area for `areaFromPath` (selector, breadcrumb, chat hidden); any other second segment is unknown.
- The sidebar marks a pelada active on `/pelada/:id` and every route below it (`isPeladaPath`). Links into a pelada (home cards, notifications, profile) open the overview.
- From md the chat is a floating button with a Popover (`PeladaChat`), hidden on Convites, Financeiro and Assinatura so it cannot cover their controls; on the other areas the layout's `<main>` keeps bottom padding (`md:pb-24`) so the fixed chat button never covers the last row. Below md the chat is a page, `/pelada/:id/chat` (`PeladaChatPage`, a child of the layout, `ChatPanel size="page"`): the layout renders it without the header, the notice and the areas, at the viewport's height, the composer above the home bar; the mobile header shows ← + the pelada's name + "12 membros" and the bottom tabs step aside. It is opened from the chat icon of the mobile header, on every area; no unread badge (the backend has no such data). `areaFromPath` doesn't know `chat` (null: not an area), `isChatPath` (`utils/mobileNav.ts`) does.
- Below md the area selector gives way to `PeladaAreaTabs`: four direct underlined links, Geral (accessible name "Visão geral"), Sessões, Membros and Ranking (`PRIMARY_PELADA_AREAS` in `utils/peladaAreas.ts`), plus a shadcn `DropdownMenu` "Mais". Every other `visibleAreas(role)` destination is in the menu under Pelada / Gestão: Prêmios, Financeiro, Convites, Configurações, Assinatura, preserving admin/creator visibility. All five controls fit at 375 px without horizontal scrolling. On a secondary area the Mais trigger is underlined and its accessible name identifies the current area; the menu's actual route link carries `aria-current="page"`. The breadcrumb stays hidden below md (the mobile header has ← and the title).
- The layout registers `usePeladaDetail.refetch` for pull to refresh and puts the chat icon and, for admins, the gear (→ `/pelada/:id/settings`) in the mobile header. A "+" item (Nova sessão, Convidar jogador) arrives as the router state `{ create }` (`createIntent`): the layout opens `CreateSessionDialog` on Sessões / `InvitePlayerDialog` on Membros from it (admins, a writable pelada for the session) and closing the dialog clears the state, so a reload doesn't open it again. Nova cobrança does the same in `FinanceTab` (the creation opens once the list is ready). The ranking's ⌘K / ⌘I / ⌘P shortcuts only listen on the Ranking page.

Session selection (`pickNextSession`, `pickRecentSessions`) and relative day labels (`formatRelativeSessionDay`) take the pelada's `timeZone` explicitly, using `todayInZone` rather than the browser's calendar day. This matches the backend's `nextDaily` and attendance-ranking period. `e2e/mobile-gestures.spec.ts` (mobile projects; touches through CDP `Input.dispatchTouchEvent`) covers the tabs, the "+" menu (admin and player, Nova sessão and Nova cobrança opening their forms once), ←, the swipe back with an emulated installed iPhone (`navigator.standalone`), not on Android nor away from the edge, and pull to refresh (the `/peladas/my` read again; a page without a registration doesn't react). `e2e/daily-navigation.spec.ts` covers route changes, delayed reads, access-denied recovery and retryable load errors in all four viewport/theme projects.

## Mobile shell

Spec: `docs/plans/2026-11-16-mobile-jakob-redesign-spec.md`. Below 768 px (`md`) the app behaves like the apps people use every day (Jakob's law): tabs at the bottom, creation in the middle, the profile in the corner, back by swiping from the edge, pull to refresh. From md nothing changes (the sidebar, the bell, the chat button). `MobileShell` (`components/layout/mobile/`, inside `AppLayout`'s `SidebarInset`) provides `MobileShellContext` and renders the header, the page (inside `PullToRefresh`), the bottom tabs and the "+" menu; the header and the tabs are `md:hidden`, the gestures only run below md.

- **Bottom tabs** (`BottomTabBar`, `nav` "Navegação principal", fixed floating `bg-card` capsule with `rounded-full` and `shadow-fab`, 64 px tall, 12 px side margins and a bottom offset of 12 px + `env(safe-area-inset-bottom)`, targets at least 48 px): Início (`/home`; also `/invitations/:id`) · Peladas (`SportShoeIcon`; `/peladas`; also `/pelada/**`, `/daily/:id`) · **+** (44 px `bg-brand` circle: the "Criar" menu) · Avisos (`/notificacoes`, a `bg-brand` badge with `unreadCount`, "20+" above 20) · Perfil (the user's avatar, `/profile/{id}`; also `/settings`, `/admin/**`). The active tab has `aria-current="page"`, an inset rounded `bg-muted` surface, `text-brand-text` and a heavier icon stroke (the free Hugeicons set has no filled icons). Tapping the active tab goes to its own page, or to the top when already there. Hidden in the chat and while the keyboard is open (`useVirtualKeyboard`: the visual viewport 150 px+ shorter than the window), as in WhatsApp. Its complete footprint (64 px + 12 px bottom gap + safe area) is `--mobile-tabbar-h` (`index.css`: 0 from md and while hidden, `html[data-tabbar="hidden"]`): `PageContainer`'s bottom padding and `SelectionBar`'s `bottom` add it. Route destinations stay native links (shadcn Tabs are for in-page panels); the center action uses `Button`, the unread counter uses `Badge` and the profile uses `PlayerAvatar`. Color/press feedback and focus rings follow the existing reduced-motion rules. Approved design: `docs/plans/2026-11-17-floating-mobile-navigation-design.md`. `tabForPath`, `isTabRoot`, `tabRoot` in `utils/mobileNav.ts`.
- **"+" menu** (`CreateMenu`, a `Drawer` "Criar"): the items come from `createActions(peladas, currentPeladaId)` (`utils/mobileNav.ts`, pure, tested), from `MyPeladasContext`: Nova sessão (admin of a pelada with a writable subscription), Convidar jogador (admin), Nova cobrança (`isFinanceManager` and writable), Criar pelada (always, `openCreatePelada`). The pelada on screen (`/pelada/:id/**`, or the session's, from `useMobileHeader({ peladaId })`) is preselected when it qualifies; otherwise with one eligible pelada it goes straight there, with several a second step "Em qual pelada?" lists them. The item navigates to the area whose page owns the form (`/pelada/:id/sessoes`, `/membros`, `/financeiro`) with the router state `{ create }` (`CreateNavState`, read with `createIntent`). A plain player sees only Criar pelada; the server still checks every action.
- **Header** (`MobileHeader`, sticky, `pt-[env(safe-area-inset-top)]`): ← on every page but a tab's own (Início shows the logo); the title is the one the page set with `useMobileHeader({ title, subtitle })` (always shown: the pelada's name over its areas, "12 membros" in the chat), else the text of the page's first `h1` once it scrolls under the header (iOS "large title": an `IntersectionObserver` on the h1, found again by a `MutationObserver` as pages render), tab roots included; the page's buttons on the right through `MobileHeaderActions` (a portal into the header; `MobileHeaderLink` for an icon link): the gear on the own profile (→ `/settings`) and on Avisos (→ `/settings#notificacoes`), the chat and (admins) the gear in a pelada. ← (`goBack` of the context) is `navigate(-1)`, or, on the first entry of the visit (a WhatsApp link, a push, a reload: React Router's `history.state.idx` is 0, also after a replace), the parent with `replace`: `useMobileHeader({ parent })` (the session page: `/pelada/{peladaId}/sessoes`) or `parentPath(pathname, userId)` (`/pelada/:id/financeiro/:listId` → the collections, other pelada pages → `/pelada/:id`, `/pelada/:id` → `/peladas`, `/settings` and `/admin` → the own profile, `/admin/**` → `/admin`, `/invitations/:id` and another player's profile → `/home`).
- **Swipe back** (`useEdgeSwipeBack`): only in the iPhone's installed app (`useSwipeBackAvailable`: `usePwaInstall` context `installed` + `isIosDevice`); Safari already has the gesture and Android's system back fires `popstate`. It starts within 24 px of the left edge with a horizontal intent (decided after 10 px), so the area strip, carousels and the teams editor's drag and drop (none starts at the edge) keep theirs; the page follows the finger over a `bg-overlay/40` veil (the previous page isn't kept mounted, so the veil is what shows behind it); released past 35 % of the width or above 0.5 px/ms it does `goBack`, otherwise it springs back. Off on a tab root and with an open overlay (`[role=dialog][data-state=open]`).
- **Pull to refresh** (`PullToRefresh` + `useRefresh(handler)`): a page registers the promise of its reads while mounted; without a registration there is no gesture. It starts at `scrollY === 0`, finger going down, no overlay open and outside inner scroll areas (the chat's messages); the page follows at half the finger's distance (capped at 96 px) and fires from 64 px; a brand spinner turns while the promises run, a second pull is ignored and a rejection toasts "Não foi possível atualizar" (the screen keeps its data; the hooks that keep their own error state resolve anyway and show it). `html` has `overscroll-behavior-y: none` below md, so Chrome's own reload (the whole app and the session boot) and Safari's bounce stay out. Registered: Início (`MyPeladasContext.reload`, the invitations, "Seus números"), Peladas, the pelada layout (`usePeladaDetail.refetch`, every area), the session (`useDailyDetail.refetch`), Avisos (`useNotifications.refresh`), Perfil (`useProfile().reload`) and Financeiro (`useFinance.refresh`, with the layout's). The reloaders return their promise (`useReload` for the hooks that reload by bumping a version).
- **Accessibility and motion:** every gesture has a one-tap alternative (WCAG 2.5.1): ← for the swipe, and the pull is a shortcut to reads that already happen (`visibilitychange`, "Tentar novamente"). Under `prefers-reduced-motion` the gestures work without the page moving, the spinner stands still and the navigation is immediate. The decisions (edge, intent, threshold, resistance, velocity) are pure functions in `utils/gestures.ts`, tested with Vitest.
- `client/index.html` has `viewport-fit=cover`, so `env(safe-area-inset-*)` works (the CSP hashes only the theme script, untouched).
- Pages that work at any width, though the desktop's navigation doesn't point at them: `/peladas`, `/notificacoes`, `/pelada/:id/chat`.
