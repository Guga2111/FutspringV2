# Frontend Documentation — Futspring Client

React single-page app in `client/`. UI text is in Portuguese (pt-BR); code identifiers are in English.

## Stack

- React 19, TypeScript ~5.9 (strict), Vite 8, Vitest 2
- **bun** as package manager — never use `npm`/`yarn`; `bun.lock` is the only lockfile
- Tailwind CSS 3.4 (`tailwind.config.js` + `postcss.config.js`, `tailwindcss-animate`), class-based dark mode
- shadcn/ui (style `default`, base color `slate`, CSS variables) on top of Radix primitives; components in `src/components/ui`
- Guided tour: `@ark-ui/react` (Ark UI `Tour`, wrapped in `components/ui/tour.tsx`; the only Ark primitive, since Radix/shadcn have no tour)
- Icons: **Hugeicons only** — `@hugeicons/react` (`HugeiconsIcon`) + the free set `@hugeicons/core-free-icons` (`<HugeiconsIcon icon={UserGroupIcon} className="size-4" />`; size with `className`, the default stroke is 1.5, `strokeWidth` where a heavier line is wanted; on standard-density screens (`devicePixelRatio` < 1.5, e.g. a 1080p monitor) `index.css` draws the default 1.5 stroke at 2, because 1.5 renders as a faint ~1px line next to Inter; an explicit `strokeWidth` is left alone). An icon stored as a value (maps such as `AREA_ICONS`, `notificationView().icon`) is typed `IconSvgElement` and rendered with `<HugeiconsIcon icon={Icon} />`. `bunx shadcn add` still generates lucide imports: swap them to Hugeicons before committing
- React Router 7 (declarative `BrowserRouter` + `<Routes>`), Axios, Sonner (toasts)
- Charts: recharts through shadcn `ui/chart.tsx`; tables: `@tanstack/react-table` v8 + shadcn `Table`
- Fonts: `@fontsource-variable/inter`, `@fontsource/barlow-condensed` (see Typography)
- `date-fns`, `react-day-picker` (shadcn `Calendar`), `cmdk` (shadcn `Command`), `vaul` (shadcn `Drawer`)
- Realtime chat: `@stomp/stompjs` + `sockjs-client`
- Drag and drop: `@dnd-kit/core` (the session's teams editor on desktop; pointer and keyboard sensors, pt-BR screen-reader announcements; native HTML5 drag and drop has neither touch nor keyboard)
- QR Codes: `qrcode.react` (`QRCodeSVG`, the app download panel of `/auth` and the desktop view of `/instalar`)
- PWA: `vite-plugin-pwa` (`injectManifest`) + `workbox-precaching` / `workbox-routing` in our own service worker `src/sw.ts` (see [PWA](#pwa))
- Forms (see [Forms](#forms-mandatory)): `react-hook-form` + `zod` 4 + `@hookform/resolvers` + shadcn `Field`
- No server-state library (no react-query): data is fetched in hooks with `useState`/`useEffect`

## Commands

Run from `client/`:

```bash
bun install
bun run dev          # Vite dev server on http://localhost:5173 (proxies /ws to :8080)
bun run build        # tsc -b && vite build
bun run lint         # ESLint 9 (flat config)
bun run test         # vitest run
bun run test:visual:docker   # Playwright visual regression in the official image (needs Docker)
bun run test:visual:update   # same, rewriting the snapshots (review the PNG diff before committing)
bunx shadcn@latest add <component>   # add a shadcn component to src/components/ui
```

CI (`.github/workflows/ci-frontend.yml`) runs `bun install --frozen-lockfile`, lint, build and test on pushes and PRs to `main`/`dev` that touch `client/`; the deploy on `main` waits for it (see CI/CD in `BACKEND.md`). Lint is blocking (0 errors; one `react-hooks/incompatible-library` warning from TanStack Table remains). Before finishing a change run `bun run lint && bun run build && bun run test`.

A second CI job, `visual`, runs the Playwright visual regression in `mcr.microsoft.com/playwright:v<version>-noble` (keep the tag equal to `@playwright/test` in `package.json`); it is not blocking yet and uploads the report when it fails. See [Visual regression](#visual-regression).

## Environment

- `VITE_API_URL` — backend base URL, read at build time (production: `https://futspring.luisgosampaio.com/api` — nginx strips `/api` before proxying, so requests go to `/api/api/v1/...`; locally it is unset). Falls back to `http://localhost:8080`. The only place that reads it is `src/lib/config.ts` (`API_BASE`), used by `api/client.ts` and `getFileUrl`.
- `RealtimeProvider` (`components/layout/`) opens one `new SockJS("/ws")` connection per logged-in user (relative), shared by the chat and the notifications: it works through the Vite dev proxy (`vite.config.ts`) and in production because the app and the API share an origin behind the reverse proxy.
- `vite.config.ts` defines `global: 'globalThis'` (needed by sockjs-client) and `__APP_VERSION__`, the short git sha of the build (`git rev-parse --short HEAD`, `"dev"` without git; `"test"` in `vitest.config.ts`), sent as `release` with the error reports.
- The backend's CORS allows `ALLOWED_ORIGINS` (default `http://localhost:5173`), so keep the dev server on that port or set `ALLOWED_ORIGINS` for the API.
- The connection needs a valid token (CONNECT without one is rejected); only members can subscribe to a pelada's topic; chat send errors arrive on `/user/queue/errors`, notifications on `/user/queue/notifications`.

Where new code goes:
- A feature's components go in `components/<feature>/`, its hooks in `components/<feature>/hooks/` (one `hooks/` per feature, never split). Hooks used by more than one feature go in `src/hooks/`.
- A feature folder holds at most **12 files directly** (`hooks/` aside); whoever adds the 13th splits it in the same PR: a group of 3 or more components about the same part of the feature goes to a sub-folder named after it, lowercase (`finance/collection`, `daily/teams`, `pelada/ranking`). A component used by two or more sub-folders, or the feature's entry point (`FinanceTab`, `DailyHeader`), stays at the feature root. `components/ui/` (shadcn primitives) and the shared components directly in `components/` are exempt. `src/lib/layout.test.ts` enforces the limit.
- Pure helpers (no React) go in `src/utils/` or `src/lib/`; form schemas in `src/schemas/<domain>.ts`.
- Import with the `@/` alias (`@/` → `src/`, configured in `tsconfig*.json`, `vite.config.ts`, `vitest.config.ts`). There are no `../` imports; don't add any.

- `PrivateRoute` only checks that a token exists (no expiry check); an expired token is caught by the 401 interceptor.
- Pages don't render a nav bar. Their `<main>` is `PageContainer` (one max width, side margins and vertical rhythm for every private page, its skeletons included) and their title goes through `PageHeader` (`PeladaPageHeader` in a pelada area); they use the `.page-enter` fade on their root.

## Data layer

### API client and auth

- `src/api/client.ts` exports the single axios instance (`apiClient`). **Only `src/api/*` imports it**; never import `axios` or call `fetch` elsewhere.
- `context/AuthContext.tsx` owns the session: token in `localStorage.futspring_token`, user in `localStorage.futspring_user`, `login(token, user)` / `logout()` / `updateUser(patch)` (an edited profile merged into the stored user), read through `useAuth()`. Nothing else touches those keys.
- `logout()` also releases this device's Web Push (best effort, never blocking the logout): clears the icon badge, sends `unsubscribePush(endpoint)` with the closing session's token and a 2 s timeout, then `subscription.unsubscribe()`. After a 401 (the session is already invalid) only the browser drops it; the server deletes the row at the push service's first 410. A 401 on that removal (a password reset or account deletion already revoked the token) is ignored by the interceptor, like `/auth/*`. Another account on the same device turns push on again with "Ativar notificações" (the permission is already granted, so no prompt).
- AuthContext registers the interceptors: the request interceptor (registered when `AuthContext.tsx` loads, so the shell's first requests already carry it) adds `Authorization: Bearer <token>`; the response interceptor (in the provider's effect) logs out on **401** and hard-redirects to `/auth`, except for `/api/v1/auth/*` requests (a wrong password is a 401 the login form shows). There is no refresh token (the JWT lasts 7 days).
- `RealtimeProvider` sends the same token in the STOMP `connectHeaders` (the chat and the notifications share that connection).

Data flows **api → hook → page/component**. A hook owns the request state; the page renders it.

- `usePeladaDetail(id)` — loads pelada, dailies, ranking and awards in parallel, each with its own loading flag; exposes `accessDenied` (403), `error`, `refetch*` (each returns its promise) `mergeDaily(item)` to merge a mutation result into the sessions list, `mergeMembers(members)` to merge members returned by a mutation (mensalista, stars, admin; one or a batch) and `dropMembers(userIds)` to take removed members out of the list. Results are keyed by pelada id and responses for another pelada are dropped, so navigating between peladas shows the skeletons, never the previous pelada's data.
- `usePeladaActions(pelada, refetchDailies, mergeDaily, mergeMembers, dropMembers)` — member actions don't hold a dialog open: the dialog closes first and the request runs in the background with a toast, each with a pending member id that disables the card's ⋯. `setMemberMensalista` (merges the returned member; `togglingMensalista`), `setMemberStars` (optimistic: merged at once, the returned member on success, the previous value back on error; `settingStars`), `toggleAdmin` (merges `isAdmin` after the success; `togglingAdmin`), `removeMember` (the card is dimmed while `removingMember`, then `dropMembers` + a background `refetchDailies`, since the backend takes the member out of upcoming sessions), the bulk actions `bulkSetAdmin`, `bulkSetMensalista`, `bulkSetStars` (not optimistic: only the response is merged) and `bulkRemove` (`dropMembers` + background `refetchDailies`), each returning `Promise<boolean>` (true on success, so the grid leaves selection mode; on error a toast and the selection stays) with `bulkPending` (the ids being changed: their cards are dimmed, the selection bar is disabled), and confirm/withdraw the caller in the next session (optimistic: `toggledAttendance` (`utils/attendance.ts`) is merged into the sessions list and the sidebar through `updateNextDaily` at once, the server's answer replaces it (a mensalista who bumps a diarista keeps the count) and an error puts the previous values back with a toast; no success toast). ### Error reporting

`lib/errorReporting.ts` sends uncaught errors to `POST /api/v1/client-errors`, which writes one log line (Loki, `event=client_error`; see Observability in `BACKEND.md`). No third party, no SDK. Sources: window `error` and `unhandledrejection` (listeners added by `installErrorReporting()` in `main.tsx`) and every route's `ErrorBoundary` (`componentDidCatch`). Errors the code catches (toasts, error states) are not reported.
- `path` is `location.pathname` only; the query and hash of every URL inside the message and the stack are removed too (`stripUrlQueries`; a reset link carries its token in the query), keeping a frame's `:line:column`.
- Each field is cut to the API's limit; `release` is `__APP_VERSION__`.
- Each message + stack is sent once and at most 10 per page load; "ResizeObserver loop…" and "Script error." without a stack (cross-origin scripts) are ignored; a failed send is ignored.
- In the visual tests a report is a POST without a fixture, so an uncaught error on a screen fails the test.

## Auth & permissions in the UI

- Admin checks in the client only decide what is **shown**. The backend enforces every rule (see "Ownership & authorization" in `BACKEND.md`); never rely on hiding a button for security.
- Pelada admin is derived in `PeladaDetailPage` (the pelada layout, shared as `isAdmin` through `usePeladaWorkspace`) from `pelada.members[].isAdmin` / `creatorId`. Session admin uses the server-provided `daily.isAdmin`; prefer server-provided flags when they exist.
- A 403 from a detail endpoint renders an "access denied" state (`accessDenied` in `usePeladaDetail`/`useDailyDetail`), not a toast loop.
- Team color can be edited by a team player or an admin (`TeamsSection`: `canEditColor = isOnTeam || daily.isAdmin`), mirroring the backend rule.

## Invitation contracts and authentication destinations

`api/invitations.ts` mirrors the `/api/v1` invitation endpoints documented in `BACKEND.md`: admin POST/GET `/peladas/{id}/invitations` (`pending` filter, `page`, `size=20`), POST cancellation scoped to the pelada, GET/POST/DELETE `/peladas/{id}/invite-link` (GET 204 → null); own GET `/invitations`, GET `/invitations/{id}`, POST accept/decline; public GET `/invite-links/{token}` and authenticated POST `/invite-links/{token}/join`. GETs only read. `invitePlayerSchema` mirrors the positive required `userId`; responses and status labels live in `types/invitation.ts`. Effective expiry comes from the backend; `useNowUntil` also disables an open individual invite at its expiry. The public preview's id is used only for membership/routing; no private detail endpoint is fetched before membership.

Acceptance reloads `MyPeladasContext` and opens the pelada. Link joining lives outside the private shell: navigation mounts the shell and loads the new membership. A link preview never auto-joins, including after login/register. Removed players receive the backend's explanation that an individual invite is required; declined players can still choose to enter by link. `PELADA_INVITATION` notifications carry nullable `invitationId` and link to the dedicated page; `MEMBER_JOINED` is an in-app admin notice. Legacy `ADDED_TO_PELADA` notifications remain readable. Membership e-mail preferences include individual invitations.

`utils/authReturn.ts` preserves a full local destination and rejects external/protocol-relative/backslash redirects. `AuthPage` retains it when switching login/register tabs. A non-auth API 401 logs out and redirects to `/auth?expired=1&returnTo=…`, preserving the full current URL; the expired-session message explains that login is required. Wrong-account invitations offer signing in with another account. Public preview GETs ignore stale backend session headers.

## Financeiro tab

`components/finance/FinanceTab` is rendered by the lazy `/pelada/:id/financeiro` route (`PeladaFinancePage`), so it downloads only when that page opens; it remounts/refetches on return. Chat is hidden on this page to keep financial controls accessible. Like every area page it has the compact header (breadcrumb, title, area selector), not the photo banner. The finance component is keyed by pelada id. The module uses the existing shell, shadcn primitives, semantic tokens, pt-BR labels and responsive lists (375px, light/dark). There are no realtime finance subscriptions or automatic attendance/mensalista changes.

`api/finance.ts`, `types/finance.ts` and `schemas/finance.ts` mirror the backend finance contracts in `BACKEND.md`. Money stays as exact two-decimal strings; form inputs accept Brazilian amounts such as `45`, `45,50` and `1.234,56`, normalized by `normalizeFinanceAmount` without floating-point arithmetic; `utils/finance.formatFinanceMoney` formats them without floating-point arithmetic. Amounts/totals/status/permissions are always supplied by the server. Collections, cash and audit use numbered pages (`ListPagination`: count, Anterior, "Página N de M", Próxima; 10 collections and 20 history rows per page, from the API's `total`); older notices of a charge load in pages of 10. List summaries omit components; list detail includes complete price components and up to 10 recent restricted notices per charge.

`FinanceTab` reads the open collection from the URL (`useParams().listId`, `/pelada/:id/financeiro/:listId`): opening a collection navigates there, "← Cobranças" and the Cobranças tab go back to `…/financeiro`, switching to another tab with a collection open replaces the URL with `…/financeiro`, and a command result for another collection (create, duplicate) navigates to it. `useFinance(peladaId, selected, select)` takes that id and the navigation; the detail and its error are kept keyed by collection id, so another collection shows the skeleton, never the previous one. The tour only starts on the list with nothing open, so whoever arrives by a link doesn't get it over the collection.

`useFinance(peladaId, selected, select, writable)` also exposes `writable` (the workspace's, through `FinanceTab`) and `locked` (`pending || !writable`): every write control (Nova cobrança, cash entries, the collection's ⋯ items except Compartilhar no WhatsApp, Selecionar, Receber / Conferir / Informar pagamento, charge corrections, reversals, the settings cards' Salvar, QR uploads, templates) is disabled while the pelada is read-only; reading, filters, pages and the WhatsApp message stay. `useFinance` loads the overview (one `scope` and page of collections) and selected detail, cancels stale results, refreshes when the browser returns to visibility, and merges command responses (`{overview,detail}`): the result's settings/permissions/balance replace the current ones but the collections on screen stay, and the current scope/page is reloaded (a change never jumps to page 1; a page that no longer exists falls back to the last one). A revision and UUID request key accompany every write. A logical submission retains its key/revision across uncertain retries; changed payloads get another key. Editors capture the revision when opened and retain it when moving between details, payment and correction sheets. A 409 refreshes current state and reports the server's conflict instead of overwriting it. The backend revalidates all permissions and child scopes, regardless of UI controls.

The tabs are **Cobranças** ("Minhas cobranças" for members), **Caixa** (whoever sees the cash), **Histórico** (responsáveis) and **Configurações** (responsáveis, and admins who aren't responsáveis with only the Responsáveis card). Only designated responsáveis get the manager view (`permissions.manage`): an admin or creator who isn't one sees the member view with an `Alert` "Você não é responsável financeiro" and a button to the Configurações tab (`appointManagers && !manage`), and gets the member tour. Collections are split into **Em aberto** / **Encerradas** chips (the API's `scope`), each with its own numbered pages. Managers see received / to-receive totals and pending-review counts; members see what they paid and what they still owe ("a pagar", highlighted, or "Pago"). Configurações is a column of `SettingsCard`s (the shared `components/SettingsCard.tsx`, each with its own footer): **Pix para receber** (key, recipient and the default QR Code via `FinanceQrField`: preview, Enviar/Trocar sent on pick, Remover), **O que os membros veem** (Individual / Transparente as a `RadioGroup` of cards), **Responsáveis financeiros** (whoever can appoint: creator, admins and responsáveis; every member, admins included with an "Admin" note, in a `FinanceMemberChecklist` (search, counter, checkboxes with avatars; the saved responsáveis listed first) inside a `Collapsible` closed by default, with the current responsáveis summarized above it) and **Modelos de cobrança** (rows with Editar, Novo modelo; unsaved starters marked Sugestão). Managers can create/edit configurable lists or reusable monthly/daily/event templates, edit default Pix/visibility, upload bank QR images and appoint other responsáveis (as do admins). At least one is required (`financeManagersSchema` `.min(1)`, the error shown under the collapsed list; the server also answers 409). Lists snapshot conditions, participants and instructions. Individual charge forms adjust components, abatements and due dates with a reason after publication. "Trocar participante" (`FinanceReplacementForm`) picks the new member in a searchable combobox (`Popover` + `Command`, like `TimeZonePicker`: avatar + name, accent-insensitive, "Nenhum membro encontrado") that leaves out everyone with an active charge in the list (`excluded` from `detail.charges`), since the server allows one active charge per person. Participant selection supports name search, mensalista/diarista filtering, manual guests and explicit review of imported daily confirmations; bulk submission is atomic. Guest names never auto-link accounts. Replacing a participant retains money on the old canceled allocation, with a new unpaid charge for the replacement.

**Tour:** the first time a user opens the page, `FinanceTour` (wrapping the tabs, `components/ui/tour.tsx`) starts a guided tour of their role: `FINANCE_MANAGER` (Nova cobrança, Em aberto / Encerradas, the list, Caixa, Configurações) or `FINANCE_MEMBER` (their charges, the chips, Caixa only in transparent mode); the steps come from `utils/financeTour.ts` (`financeTourSteps(manage, viewCash)`) and point at `data-tour` attributes in `FinanceTab`. It only starts automatically on the collections list with nothing open over it. Finishing, closing (✕, Esc, click outside) or "Pular" marks it seen on the server (`/tours`), so it doesn't start again on any device. The "?" button next to Atualizar (`FinanceTourButton`) closes any sheet, goes back to the collections list and restarts it.

A saved template is an optional "Começar de um modelo" `Select` at the top of the first step (fills the form; one with items opens the options). Disclosures are section rows, not buttons. `FinancePeoplePicker` is shared with later additions and supports multiple guests. Simple price mode ignores inactive component fields; detailed mode validates and sums them exactly.

**Selection: Receber selecionados and Ajustar valor:** on a draft or open list, managers get an outline "Selecionar" next to the search (in any queue chip, while some charge can be selected). With 1+ selected, the shared `SelectionBar` sits at the bottom: "4 selecionados · R$ 180,00 a receber" ("· 1 fora do filtro" when some are hidden), then, as in Membros, each action counts only what it changes (`planBulkFinanceActions(selected)`): from md "Selecionar mensalistas (N)", **Ajustar valor (N)** (outline) and **Receber (N)** (brand, open lists only; disabled with "Nenhum selecionado pode receber agora" in the bar when no selected charge can be received), the select-all toggle from lg; below md a "Mais ações" ⋯ menu (select-all, mensalistas, Ajustar valor) + Receber; ✕. Esc or ✕ exits. Ajustar valor opens the Sheet `FinanceBulkChargeForm` ("Ajustar valor de 8 participantes", `makeFinanceBulkAdjustSchema(published)`): the components (`useFieldArray`) prefilled with the list's, the adjustment at 0,00, a live "Cada um passa a dever R$ 5,00 · total R$ 40,00" (`bulkAdjustSummary`, no floating point), "2 tinham um valor próprio e passam a ter este" when some selected charges differed from the list, the reason (required after publication) and "Ajustar 8 participantes" (brand); due dates are not touched. Audit operations are named by `financeAuditLabel` ("Cobrança publicada", "Valor de participante ajustado", "Participante trocado", "Sessão desvinculada"…). Notice and payment dates/times are shown in the pelada's zone (`formatInZone`; `FinanceTab` receives `timeZone` from the workspace and passes it to `FinanceChargeDetails` / `FinanceNotices`). ## Types

- `src/types/*` — API response DTOs, matching the backend field names exactly. The backend uses Java records; boolean flags remain `isAdmin`, `isFinished`, `isConfirmed`, and `isMensalista`. PR4 removes only their unused duplicate aliases `admin`, `finished`, `confirmed`, and `mensalista`; client payloads, types, schemas, and behavior are unchanged. Omitted create-pelada settings still default to 2 teams / 5 players per team; partial updates still leave null or omitted fields unchanged.
- Deleted accounts: `PublicUser`, `PlayerDTO` and the chat `SenderDTO` carry `isDeleted`; such a player is named "Ex-jogador" by the API and drawn with `PlayerAvatar deleted` (the neutral avatar). They never appear in current lists (members, rankings), so the profile links there stay as they are.
- `src/api/*` — request payload types next to the function that sends them.
- Component prop types and view models stay next to the component/hook that owns them.
- Status values use a union type and typed maps (`types/daily.ts`, `DailyStatusBadge`; `invitationStatusLabel` / `invitationStatusStyle` in `types/invitation.ts`; `financeChargeStatusLabel` / `financeChargeStatusStyle` and `financeListStatusStyle` in `types/finance.ts`); do the same for new enum-like fields:

```ts
export type DailyStatus = "SCHEDULED" | "CONFIRMED" | "IN_COURSE" | "FINISHED" | "CANCELED"

export const dailyStatusLabel: Record<DailyStatus, string> = {
  SCHEDULED: "Agendada",
  CONFIRMED: "Confirmada",
  IN_COURSE: "Ao vivo",
  FINISHED: "Finalizada",
  CANCELED: "Cancelada",
}
```

`Record<Enum, …>` makes TypeScript fail when a value is added, instead of `switch`/`if` chains spread across components.

## Forms (mandatory)

Every new form, and every existing form you substantially change, uses **react-hook-form + a zod schema + shadcn `Field`**. Don't validate with `useState`, hand-written `validate()` functions or `FieldErrors` objects. References: `ResetPasswordForm` + `useResetPasswordForm` (`schemas/auth.ts`, client-only confirmation with `.refine`), `CreateSessionDialog` (`schemas/daily.ts`, zod input/output types for a nullable date) and `ProfileCard` + `useProfileSettings` (`schemas/user.ts`, `schemas/upload.ts`). The pelada settings cards (`components/pelada-settings/`, `schemas/pelada.ts`) are the reference for a page of independent forms: one `useForm` per card, a cross-field `superRefine` (`peladaSlotsSchema`: the mensalista limit against the capacity being edited), a file kept outside the form (`InfoCard`) and client-only typed-name confirmations (`makeDeletePeladaSchema`, `makeTransferPeladaSchema`). Still on `useState`: `CreatePeladaModal`, `FinalizeModal`, `ImportFromMessageModal`; migrate them as they are touched. `ResultsDialog` (`useResultsForm`) is the reference for a form with a field array.

Rules:

1. **One schema per form in `src/schemas/<domain>.ts`**, copying every constraint of the backend request DTO (`@NotBlank` → `.min(1)`, `@Size(min = 3, max = 30)` → `.min(3).max(30)`, `@Min(0)` → `.min(0)`, `@Email` → `.email()`), messages in Portuguese, with a comment naming the DTO it mirrors. Derive the type with `z.infer`.
2. **Keep schemas in sync with the backend**: a DTO change updates its schema in the same change.
3. **`useForm` + `zodResolver(schema)`** with complete `defaultValues` (never `undefined`).
4. **Fields go through `Controller` + `Field`**: `data-invalid` on `Field`, `aria-invalid` on the control, `FieldLabel htmlFor` matching the control `id`, `FieldError` for the message, correct `type`/`autoComplete`.
5. **Native `<form onSubmit={form.handleSubmit(onSubmit)} noValidate>`**, submit `Button type="submit" disabled={form.formState.isSubmitting}`. Use `formState.isDirty`/`isSubmitting` and `form.reset(values)` instead of extra `isLoading`/`hasChanges` state.
6. **Map backend errors**: the validation 400 body is `{status, message, timestamp, errors: {field: message}}`; other errors are `{status, message, timestamp}`. Put field errors on the fields and the rest on `root`, shown in an `Alert variant="destructive"`, with `applyServerErrors(form, error, fallback)` (`lib/form-errors.ts`); outside forms use `getErrorMessage(error, fallback)` (`lib/errors.ts`) — never per-component casts.
7. **File inputs** validate size (5 MB) and type (`image/jpeg`, `image/png`, `image/webp`) with `schemas/upload.ts` (`validateImageFile`, `IMAGE_ACCEPT`), matching `FileUploadService`.

```ts
// src/schemas/user.ts
import { z } from "zod"

// mirrors UpdateProfileRequest
export const profileSchema = z.object({
  username: z.string().trim().min(3, "Mínimo de 3 caracteres").max(30, "Máximo de 30 caracteres"),
  position: z.enum(["GOLEIRO", "ZAGUEIRO", "MEIO", "ATACANTE"]),
  stars: z.number().int().min(1).max(5),
})
export type ProfileValues = z.infer<typeof profileSchema>
```

```tsx
const form = useForm<ProfileValues>({
  resolver: zodResolver(profileSchema),
  defaultValues: { username: user.username, position: user.position, stars: user.stars },
})

async function onSubmit(values: ProfileValues) {
  try {
    const updated = await updateUser(user.id, values)
    form.reset(values)
    onSaved(updated)
    toast.success("Perfil atualizado")
  } catch (error) {
    applyServerErrors(form, error, "Não foi possível salvar o perfil")
  }
}

return (
  <form onSubmit={form.handleSubmit(onSubmit)} noValidate>
    <FieldGroup>
      <Controller
        name="username"
        control={form.control}
        render={({ field, fieldState }) => (
          <Field data-invalid={fieldState.invalid}>
            <FieldLabel htmlFor="username">Nome de usuário</FieldLabel>
            <Input {...field} id="username" autoComplete="username" aria-invalid={fieldState.invalid} />
            <FieldError errors={[fieldState.error]} />
          </Field>
        )}
      />
    </FieldGroup>
    {form.formState.errors.root && (
      <Alert variant="destructive"><AlertDescription>{form.formState.errors.root.message}</AlertDescription></Alert>
    )}
    <Button type="submit" disabled={form.formState.isSubmitting}>Salvar</Button>
  </form>
)
```

## PWA

The app installs on the home screen (spec: `docs/plans/2026-11-06-pwa-web-push-spec.md`; Web Push since its third part).

- **Build:** `vite-plugin-pwa` in `vite.config.ts` with `strategies: "injectManifest"`, `registerType: "prompt"`, `injectRegister: false`. It generates `manifest.webmanifest` (`id`/`scope` `/`, `start_url` `/home` (logged out, `PrivateRoute` sends it to `/auth`), `display: standalone`, `lang: pt-BR`, background/theme `#F7F7F9` (the light page; the `theme-color` meta still follows the theme live), icons 192 / 512 / maskable 512) and injects its `<link rel="manifest">`. `index.html` has the iOS tags (`apple-touch-icon` 180 PNG, `apple-mobile-web-app-title` / `-capable` / `-status-bar-style`).
- **Service worker (`src/sw.ts`):** `precacheAndRoute(self.__WB_MANIFEST)` + `cleanupOutdatedCaches()`, and a `NavigationRoute` to `index.html` whose `denylist` leaves `/api`, `/ws` and `/files` to the network. **No API response is cached** (stale attendance, spots or finance cause real mistakes): offline, only the shell opens and the screens show their error states. The precache takes the build (`js, css, html, woff2, webp, png, svg`) except `landing/**` (large photos), the 512 icons (read only at install) and the Inter subsets other than Latin (fetched by `unicode-range` only for characters pt-BR doesn't use); `.jpg` isn't in the pattern. A `SKIP_WAITING` message activates a waiting version.
- **Updates:** `components/layout/PwaUpdater` (mounted in `main.tsx`, so public pages too) registers it with `useRegisterSW` (`virtual:pwa-register/react`) and, when a new build is waiting, shows a toast that stays ("Nova versão disponível · Atualizar" → `updateServiceWorker(true)`); never on its own, which would reload in the middle of a form. `bun run dev` has no service worker (the plugin's default); try it with `bun run build && bun run preview`.
- **Offline:** `useOnline()` drives the shell's "Sem conexão" `Alert` (`AppLayout`).
- **Web Push** (`api/push.ts`, `usePushSubscription`, `lib/push.ts`): standard VAPID push, each browser through its own push service. `src/sw.ts` handles `push`: reads the backend's JSON (`PushPayload {title, body, url, tag, unreadCount}`) and **always** shows a notification (`icon` `/pwa-192.png`, `badge` `/pwa-badge-96.png`, `tag`: a newer one of the same session replaces it, `data.url`), even with the app open (Safari revokes a subscription that receives a push without showing one), and sets the icon badge (`setAppBadge` / `clearAppBadge` with 0). `notificationclick` closes it and, with an app window open, `focus()` + `navigate(url)`, else `clients.openWindow(url)`. `pushsubscriptionchange` isn't handled: `syncPushSubscription` sends the subscription again when the app opens. The worker has no token, so it marks nothing read: the url carries `?notificacao={id}` and `useNotifications` does it. The app also syncs the badge with the bell's counter and clears it on logout. Entry points: the Home `EnablePushCard` (installed app, status `inactive`: "Ative as notificações" + "Ativar notificações"; ✕ stores the date in `localStorage.push_card_dismissed`, back after 30 days) and the "Neste aparelho" block of `/settings#notificacoes`. A toast (STOMP) and a system notification both show with the app open: accepted in V1.
- **Install:** `captureInstallPrompt()` (`lib/installPrompt.ts`, called in `main.tsx` before the render, because Chrome can fire `beforeinstallprompt` before any page mounts) keeps the event; `usePwaInstall()` turns user agent, touch points, `display-mode: standalone` / `navigator.standalone` and the event into an `InstallContext` (`utils/pwaPlatform.ts`: `installed`, `ios-safari`, `ios-other`, `in-app`, `android-prompt` (Android only; desktop Chrome gets the QR Code), `android-manual`, `desktop`). Entry points: `/instalar`, `InstallAppCard` on Home and the `/auth` QR Code.
- **Icons:** generated from `public/gerrard.webp` with `sips` (the largest logo there is, so the 512 ones are upscaled; regenerate from a vector logo when there is one): crop the 2 px border, resize, pad with its background `#9E9C96`:
  ```bash
  sips -s format png --cropToHeightWidth 158 186 public/gerrard.webp --out /tmp/src.png
  # name, logo width, square size: pwa-192.png 184 192 · pwa-512.png 490 512 · pwa-maskable-512.png 330 512 (inside the 80% safe area) · apple-touch-icon.png 172 180
  sips --resampleWidth 490 /tmp/src.png --out /tmp/t.png && sips --padToHeightWidth 512 512 --padColor 9E9C96 /tmp/t.png --out public/pwa-512.png
  ```
- **Server cache:** `sw.js`, `manifest.webmanifest` and `index.html` must be served with `Cache-Control: no-cache` (hashed assets keep the long cache), or a phone can stay on an old version for days: nginx config in CI/CD of `core/docs/BACKEND.md`.

## Performance

- **Code splitting:** every page is `React.lazy`; keep heavy libraries (recharts, tanstack table) inside the pages that use them. A dialog that pulls a heavy library into a page is lazy-loaded on first open (reference: `PlayerHistoryDialog` in `PeladaDetailPage`).
- **Requests:** never fetch in a loop per item; ask the backend for an endpoint that returns what the screen needs (as `nextDailyDate` and `/users/{id}/peladas` do).
- Don't load every tab up front when a tab is expensive; fetch on first open.
- After a mutation, merge the returned DTO into state instead of refetching the whole detail when the endpoint already returns it.
- `await` only functions that return a promise; a refetch must return its promise if the caller waits for it.
- **Memoize** derived lists that sort/filter on every render (`useMemo`), and stabilize callbacks passed to effects (`useCallback`). Don't sprinkle `React.memo` without a measured problem.
- **Images:** `loading="lazy"` and explicit `width`/`height` on avatars, banners and photos below the fold; keep static assets small: resized WebP, not full-size PNG (the logo is `public/logo-64.webp`, about 3 KB; the favicon `public/gerrard.webp`, about 5 KB).
- **Lists:** paginate long histories (chat, match history) rather than rendering everything.
- **Debounce** search inputs (300 ms, as `InvitePlayerDialog` does).
- **Realtime:** there is no polling. The bell is live (one STOMP connection per user, `RealtimeProvider`); session pages update only on reload or after the user's own mutation. If polling is added, put it in the feature hook, pause it when the tab is hidden (`visibilitychange`), stop it when the daily is `FINISHED`/`CANCELED`, and clear the interval on unmount.
