# API: peladas, invitations and sessions

> Peladas, members, invitations and dailies. Part of the [backend guide](README.md).

All routes are under `/api/v1`. "Auth" is the relationship checked (see the matrix); the invitation-link preview and the e-mail preference links are also public (see below).

## Membership invitations (`PeladaInvitationController`)

| Method | Path | Auth | Response |
|--------|------|------|----------|
| GET | `/invitations?page=0&size=20` | recipient | `List<InvitationDTO>`: own unexpired pending invitations only; size 1–50 |
| GET | `/invitations/{id}` | recipient | `InvitationDTO {id, peladaId, pelada: PeladaPreviewDTO, recipient: PublicUserDTO, sender: PublicUserDTO, status, createdAt, expiresAt, respondedAt, canceledAt, isMember}`; another account gets 403, missing id 404 |
| POST | `/invitations/{id}/accept` | recipient | `JoinPeladaDTO {peladaId}`; atomic, repeated acceptance succeeds without rejoining a removed member or notifying again |
| POST | `/invitations/{id}/decline` | recipient | 204; repeated decline succeeds, incompatible/expired status 409 |
| GET | `/invite-links/{token}` | public | `PeladaPreviewDTO {id, name, image, dayOfWeek, timeOfDay}`; id is routing metadata, no location/members/history; 410 for invalid/revoked/expired links |
| POST | `/invite-links/{token}/join` | authenticated | `JoinPeladaDTO`; 403 if removed and still blocked; 410 for invalid/revoked/expired links; existing member succeeds without a duplicate membership or notification |

The old `POST /peladas/{id}/players` direct-add operation was removed. The creator still joins their own pelada automatically. `pelada_members` contains effective members only. `PeladaInvitationService` owns the invitation lifecycle: `PENDING`, `ACCEPTED`, `DECLINED`, `CANCELED`, `EXPIRED`. Both individual invitations and share links expire **exactly 7 days** after creation, using the injected backend `Clock`; acceptance requires `now < expiresAt`. GETs never mutate, consume or join. Expired pending rows are materialized as `EXPIRED` only before replacement to release the unique index; read DTOs always compute effective expiry without a job.

Individual acceptance and membership creation share a transaction. Joining follows the subscription's member cap (see [Subscriptions](subscriptions.md#subscriptions-domainsubscription)): 409 for a `TRIAL`/`PENDING` pelada with 30 members, 402 for a read-only one; an existing member accepting again or re-entering by link still succeeds. New members are diaristas, never admins, and have no attendance confirmed; session capacity does not cap membership. A link join resolves an unexpired pending invitation as accepted while keeping previous refusals unchanged. Declining only prevents a new individual invitation for 7 days after the response; voluntary link entry remains possible. Removing a member records a block, cancels pending invitations, and preserves sporting history; only acceptance of a **new** individual invitation clears the block. Pre-release removals cannot be reconstructed and are not retroactively blocked. The sender leaving the admin role does not invalidate their invitations or links.

Every invitation/link write and member removal locks the pelada row **before** reading/changing invitation, link, membership or block state. Admin changes, creator transfer and pelada deletion use the same first lock. Initial invitation/link lookups return scalar parent ids, so a concurrent cancellation/revocation cannot leave a stale managed child in the answering transaction. Concurrent accepts are idempotent, with one member and one set of notifications. Notifications are stored in the same transaction and delivered through the existing after-commit mechanism.

`InviteLinkTokens` signs the stored record id with HMAC-SHA256 under a key derived from `JWT_SECRET` with context `pelada-invite-link`. Deterministic reconstruction lets any current admin copy the same token; the database owns expiry/revocation. Replacing a link revokes the old row and flushes before inserting. Quotas: `InvitationRateLimiter` shares **10 creations/replacements per minute per actor and pelada**; pending resends do not consume another creation. `AuthRateLimitFilter` allows **60 public previews per minute per IP**, across all tokens, with a bounded Caffeine cache and 429 responses. These in-memory quotas retain the single-instance constraint. The preview ignores stale Authorization headers; authenticated joining always verifies the session.
