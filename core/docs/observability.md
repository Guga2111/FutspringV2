# Observability

> Probes, metrics, logs, dashboards, alerts and the load test. Part of the [backend guide](README.md).

## Rules

1. No e-mail, token, password, Pix key, request body or query string in logs: log ids.
2. A new domain metric goes in the metrics table here; one worth waking someone up for gets a rule in `ops/observability/grafana/provisioning/alerting/rules.yml`.
3. The load test never runs against production.

## Observability

- **Probes:** `/livez` and `/readyz` on the main port (public), the rest of Actuator on `management.server.port=9091` (internal, never published, but reachable from the `observability` network): only `health` (status, no details) and `prometheus`. `metrics`, `threaddump` and the rest are opened on demand with `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE` (the load test does it on its own container; in production only temporarily, through the compose environment). The image's `HEALTHCHECK` and the deploy's `healthy` wait use readiness on 9091; the `deploy.yml` smoke test uses `<API_URL>/readyz`.
- **Metrics** (Micrometer, Prometheus format at `:9091/actuator/prometheus`, tag `application=futspring`): the built-in JVM (heap, GC, threads), Hikari, Tomcat, `http.server.requests` (with percentile histograms), `tasks.scheduled.execution` and the rate-limit Caffeine cache (`cache="futspring.ratelimit"`), plus the domain ones:

  | Metric | Type | Where |
  |--------|------|-------|
  | `futspring.email.queue.size` | gauge | `NotificationEmailDispatcher` executor queue |
  | `futspring.email.sent` (`result=ok\|failed`) | counter | `NotificationEmailDispatcher`, each send |
  | `futspring.email.dropped` | counter | `NotificationEmailDispatcher`, full queue |
  | `futspring.session.open` (`result=ok\|error`) | counter | `RefreshSessionService`, each session opened (verified login, password change); error = Redis |
| `futspring.session.refresh` (`result=ok\|invalid\|error`) | counter | `RefreshSessionService`, each `/auth/refresh` with an allowed origin |
| `futspring.ratelimit.rejected` (`route`: the logical name, `login`, `export`, `client-errors`, `invite-preview`…) | counter | `AuthRateLimitFilter`, each 429 |
  | `futspring.notifications.push` (`result=ok\|failed`) | counter | `NotificationPushService`, each STOMP send |
  | `futspring.webpush.sent` (`result=ok\|gone\|failed`) | counter | `WebPushDispatcher`, each Web Push send (gone = 404/410, the subscription was deleted) |

- **Logs:** ECS JSON on stdout (`logging.structured.format.console=ecs`, `service.name=futspring-api`): `@timestamp`, `log.level`, `log.logger`, `message`, `process.thread.name`, the exception as `error.type` / `error.message` / `error.stack_trace` inside the same line. Docker keeps them in `json-file` (10 MB × 3); Alloy ships every container's output to Loki (14 days), labelled `service` (the compose service: `futspring-api`), `project`, `container` and `level` (from `log.level`). In Grafana → Explore → Loki: `{service="futspring-api", level="ERROR"}`, `{service="futspring-api"} | json | log_logger=~".*WebPush.*"`. **Errors of the web app** (`POST /client-errors`) are WARN lines of `ClientErrorService` with the message "Erro no cliente em {path}: {message}" and the key-value pairs `event=client_error`, `client_path`, `client_source`, `client_release` (the build's git sha), `client_user_agent`, `client_stack` as fields of the JSON line: `{service="futspring-api"} | json | event="client_error"`. **No personal data in logs:** never an e-mail, token, password, Pix key, request body or query string; log ids (`user {}`, `notification {}`). `spring.datasource.hikari.data-source-properties.logServerErrorDetail=false` keeps PgJDBC's `Detail: Key (email)=(…)` out of exception messages, so a constraint violation logged by Hibernate or `GlobalExceptionHandler` carries only the constraint name. Tests keep plain text (the test `application.properties` doesn't set the format); `StructuredLoggingTest` checks the production format from the main file.
- **Stack:** Prometheus + Grafana + node-exporter + cAdvisor + Loki + Alloy (+ a read-only Docker API proxy) in `ops/observability/` (README there), shared by the VPS, deployed by `deploy-observability.yml`. The API joins the external `observability` network and is scraped at `futspring-api:9091` (the compose service name: Tomcat rejects the container name's underscore in `Host`). Grafana at `https://grafana.luisgosampaio.com` (login only) has the provisioned **Futspring** dashboard (requests, latency, errors, JVM, threads, Hikari, e-mail, pushes, Web Push, 429s, container CPU/RAM) plus JVM (Micrometer), Node Exporter Full and cAdvisor, and the Loki datasource (uid `loki`) for the logs.
- **Alerts:** Grafana alerting, provisioned from `ops/observability/grafana/provisioning/alerting/` (read-only in the UI), sends every alert and its resolution to Telegram: API down (2 min), 5xx > 1% (5 min, with a minimum of traffic), Hikari pending connections (5 min), host disk > 85%, heap > 90% (10 min), the API container restarting (a deploy, which recreates it, doesn't count), failed or dropped notification e-mails, more than 10 failed Web Push in 15 min, any session not stored or refreshed in Redis in 5 min and more than 20 `event=client_error` lines in 10 min (Loki). Table, thresholds and how to silence one in the README there. A new metric worth waking someone up for gets a rule in `rules.yml`.
- **Load test:** `ops/loadtest/run.sh <label>` builds the image and runs it locally with the production limits (`--cpus=1 --memory=1g`), Postgres 17 and the dev seed, logs in as the seed admin and runs `oha` with a random mix of `GET /peladas/my`, `/peladas/{id}`, `/dailies/{id}`, `/peladas/{id}/ranking`, `/peladas/{id}/attendance` at 50 / 200 / 500 connections for 60 s each (`CONCURRENCY`, `DURATION`, `SKIP_BUILD`, `IMAGE` override). Needs Docker, oha, Python 3 and Node 22+ (the native WebSocket STOMP probe). A real STOMP CONNECT / SUBSCRIBE / SEND / MESSAGE against the disposable seed runs before warm-up, followed by an internal actuator thread dump (the script opens `metrics` and `threaddump` on its container with `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE`); no production route is added. The table (RPS, p50/p95/p99, non-2xx, sampled live platform threads and Hikari pending) goes to `ops/loadtest/results/<label>-<date>.md`; `JFR=1` records `jdk.VirtualThreadPinned` with a **0 ms threshold**, counting all events, those **>20 ms**, and their maximum duration (`jfr-summary.py` parses ISO-8601 durations including minutes/hours). Use a local JDK 25 (`JAVA_HOME`) to read the recording. The report includes image ID, container health, HTTP status distribution, exception counts and timeout durations; the full synthetic API log is retained locally as a gitignored `*-api.log`. `jvm.threads.live` and the actuator dump show platform threads only; absence from that dump does not prove virtual execution (the integration test verifies it). Never against production. Local acceptance and the comparison with PR1/PR2 are recorded in the PR3 design entry; deployment and one week of Grafana observation remain separate acceptance steps.
