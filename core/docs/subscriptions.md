# Subscriptions

> Subscription state, the read-only lock, the member cap, Pix claims, notices and prices. Part of the [backend guide](README.md).

## Rules

1. Every command that writes sporting or financial data calls `SubscriptionGuard.requireWritable` right after its permission check, with a 402 case in `SubscriptionReadOnlyTest`.
2. The effective state is computed by `SubscriptionState.of(subscription, now)`; no job changes `kind`.
3. Jobs skip peladas that aren't writable.
4. A price change updates `SubscriptionPlans` and its mirror in `client/src/utils/subscription.ts` together.

## Subscriptions (`domain/subscription`)

Spec: `docs/plans/2026-11-07-subscriptions-platform-admin-spec.md`. The model, the state and the lock exist. The members read the state as `subscription: SubscriptionSummaryDTO {status, validUntil, writable}` on `GET /peladas/my`, `/users/{id}/peladas`, `/peladas/{id}` and `/dailies/{id}` (`SubscriptionGuard.summary` / `summaries`, the same `SubscriptionState` as the lock; null for a pelada without a row, which the client reads as writable like the guard); the web app shows a notice and disables the locked buttons, and a 402 that still happens shows its message in a toast. The platform admin operates every subscription through `/platform/**` (see [Platform admin](api-billing.md#platform-admin-platformcontroller-platform)); the creator pays from the Assinatura area (see [Assinatura](api-billing.md#assinatura-subscriptioncontroller-peladasidsubscription)).

- **Effective state:** `SubscriptionState.of(subscription, now)`, a pure function (no job changes `kind`): `TRIAL` before `validUntil`, then `READ_ONLY` (no grace); `PAID` → `ACTIVE` before `validUntil`, `PAST_DUE` for 7 more days (`SubscriptionState.GRACE`), then `READ_ONLY`; `PENDING` → `PENDING`; `CANCELED` → `READ_ONLY`; `EXEMPT` → `EXEMPT`. `SubscriptionStatus.writable()` is true for `TRIAL`, `ACTIVE`, `PAST_DUE`, `EXEMPT`.
- **A new pelada** (`PeladaService.createPelada` and the dev seed call `SubscriptionService.start`): when the creator's `trialUsedAt` is null, a `TRIAL` of 30 days (`TRIAL_LENGTH`) and `trialUsedAt = now`, taken by a conditional `UPDATE … WHERE trial_used_at IS NULL` (`UserRepository.markTrialUsed`; increments `rowVersion`, then refreshes the managed creator), so two peladas created at once can't both get it; otherwise `PENDING`. A `CREATED` event is recorded with the creator as actor. Transferring the pelada keeps its subscription and gives no trial to either side.
- **Lock (`SubscriptionGuard`):** every command that writes a pelada's sporting or financial data calls `requireWritable(pelada)` right after its permission check; when the state isn't writable it answers **402** "Esta pelada está em somente leitura. Renove a assinatura para voltar a usar." (its own status, so the client can offer to renew). Locked: create / change status (cancelling excepted) / delete a session (checked under the pelada lock), populate, champion photo (`DailyService`, `DailyImportService`, `DailyFinalizeService`); confirm, self, by an admin and "Confirmar todos" (`DailyAttendanceService`); sort, swap, save, rename and colour teams (`DailyTeamManagementService`); results and finalize (`DailyResultsService`, `DailyFinalizeService`); every finance write, once in `FinanceTransactions.execute` after the idempotent replay (a retry of a command that committed before the lock still answers its stored result); the player's payment report and the QR / receipt uploads are checked again before the image is decoded (`requireWritableUpload`). A session that is already live when the pelada locks can't take results or be finalized. Free: withdrawing (self and by an admin) and cancelling a session, so an upcoming session can still be fixed or called off; reads, chat, pelada settings and photo, members (admin, stars, mensalista, remove), invitations and links, transfer, deleting the pelada, `bumps/seen`, notifications, the account. A pelada with no subscription row (none in production: V19 backfill and creation) is writable and logged as a warning. The jobs skip read-only peladas: `DailySchedulerService` creates no session, `ScheduledNotificationJob` sends no reminder.
- **Member cap (`SubscriptionGuard.requireRoomForMember`):** someone new joining (accepting an invitation or entering by link) is checked in `PeladaInvitationService.join`, under the pelada lock the flow already holds: `TRIAL` / `PENDING` with `TRIAL_MEMBER_CAP` (30) members or more → **409** "Esta pelada está no período de teste, que vai até 30 membros. Peça ao criador para assinar."; `READ_ONLY` → **402** (the read-only message) whatever the count (current members stay, nobody new comes in); `ACTIVE`, `PAST_DUE`, `EXEMPT` and a pelada without a row have no cap. Inviting and creating links stay free; a refused accept rolls back, so the invitation stays pending.
- **Pix claim ("Já fiz o Pix"):** `SubscriptionService.claimPix`, under the pelada row lock. The first claim records `pixClaimedAt` and `claimedPlan` with a `PIX_CLAIMED` event; another plan only changes `claimedPlan` (the date stays, so the panel's oldest-first queue keeps its order) with an event; the same plan again changes nothing. An `EXEMPT` pelada → 409; a read-only one can claim (that's how it gets unlocked). Recording a payment or exempting clears the claim. Only a new claim (not a plan change or a repeat) publishes `PixClaimedEvent`, which notifies every platform admin (`SUBSCRIPTION_PIX_CLAIMED`), so a claim after a payment is new again.
- **Notices (`SubscriptionNoticeJob`):** every day at 09:00 in São Paulo, `SUBSCRIPTION_ENDING` to the creator of a `TRIAL` / `PAID` subscription whose `validUntil` is in `(now, now + 5 days]`, and `SUBSCRIPTION_PAST_DUE` to the creator of a `PAID` one in its grace (`validUntil` in `(now − 7 days, now]`). Each notice stores the `validUntil` it was about; the queries skip a pelada already told about that validity (`NOT EXISTS` on pelada + type + `validUntil`; `uq_notifications_subscription` is the production backstop), so a repeated or late run never duplicates and a renewal (a new `validUntil`) gets its own notice. Two queries, then each pelada in its own `TransactionTemplate` (a failing one rolls back alone, logged). The current creator gets it (a transfer moves it).
- **Prices:** `SubscriptionPlans.price(plan, memberCount)`: R$ 19,90 monthly / R$ 199,00 annual, above 40 members R$ 29,90 / R$ 299,00. The amount actually charged is stored on each payment. The list prices, the 40-member band and the trial's 30 days / 30 members are mirrored in `client/src/utils/subscription.ts` for the public landing page: change both together.
- **Deleting a pelada** (any state) deletes its subscription and events and detaches its payments (`peladaId = null`, names kept).
- After the deploy, by SQL (the ids are not in the code): `UPDATE pelada_subscriptions SET kind = 'EXEMPT' WHERE pelada_id = …` and `UPDATE users SET platform_admin = true WHERE id = …`.
