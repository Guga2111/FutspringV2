# Notification delivery

> Notification e-mails, unsubscribe links and Web Push. Part of the [backend guide](README.md).

## Rules

1. A notifying feature publishes a domain event and adds a `NotificationType` value (with its CHECK migration and `NotificationContent` case).
2. The actor is never notified.
3. Rows are written in the publisher's transaction; push, e-mail and Web Push go after the commit and fail independently.
4. Unsubscribe links are signed, expire in 30 days and only act through a POST; re-enabling is authenticated.
5. A Web Push payload carries nothing beyond what the bell shows.

## Notification e-mails

- **When:** the type is emailable (`NotificationType.emailable`), the recipient's category is on (their `notification_preferences` row, else `NotificationCategory.defaultEmail`) and the sender is real (`EmailSender.enabled()`; the no-op only logs). The preferences of every recipient of a batch are read in one query.
- **Dispatch:** `NotificationDelivery` calls `NotificationEmailDispatcher.dispatch(ids)` after the commit; it only queues a task on its **own** single-platform-thread `ThreadPoolTaskExecutor` (core = max = 1, queue of 500), unchanged by virtual threads. The executor is created by the dispatcher, not exposed as a bean: an `Executor` bean would replace Spring Boot's default `@Async` executor. The task builds the e-mails in a short read-only transaction (`findAllByIdInWithRefs` + preferences) and sends them **outside** it, one by one, through `EmailPacer` (Bucket4j: one send every 500 ms, no burst, so never more than Resend's ~2 requests/s; 30 e-mails ≈ 15 s). A full queue, a failed build or a failed send is only logged; no retry. The Resend batch endpoint isn't used because it doesn't take attachments (the logo is `cid:`). Metrics: `futspring.email.queue.size`, `futspring.email.sent{result=ok|failed}`, `futspring.email.dropped` (full queue).
- **Text and template:** `NotificationContent.of(notification)` (shared with the Web Push) is an exhaustive `switch` over `NotificationType` (a new type doesn't compile without its subject, title, body and CTA); the dates come from `AttendanceWindow` in the pelada's zone. `NotificationEmail` fills `resources/email/notification.html` (same structure and inline logo as the reset e-mail) in one pass, HTML-escaping every value, so a pelada or user name can never fill another placeholder.
- **Unsubscribe:** the footer says which category is on and links to "Desativar" (`${app.frontend-url}/notifications/unsubscribe?token=…`, a page that POSTs the token) and "Preferências" (`/settings/notifications`). The token (`UnsubscribeTokens`) is `base64url("userId:CATEGORY:version:expiresAt")` + `.` + HMAC-SHA256, keyed by an HMAC of `JWT_SECRET` with the context `"notification-unsubscribe"`; not stored, valid for 30 days, revocable through the user preference version, and only turns that category off. Every e-mail also carries `List-Unsubscribe: <${app.api-url}/api/v1/notifications/unsubscribe?token=…>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058), so Gmail / Yahoo can unsubscribe with a POST straight to the API.
- **Quota:** production is on Resend's free plan (100 e-mails/day, 3,000/month, shared with the password reset). That is enough at today's scale (it takes roughly 30 peladas of 40 players to matter); if it gets tight, the plan upgrade or the daily digest (phase 2) are the next steps. `SESSION_REMINDER` (Attendance, on by default) adds about one e-mail per unconfirmed mensalista per session; `DIARISTA_WINDOW_OPEN` is Session (off by default).
- The password reset e-mail stays separate: transactional, not a notification, no unsubscribe.
- **Link revocation:** V24 adds users.email_link_version (0). Unsubscribe payload is userId:category:version:expiresAt, context-derived HMAC-SHA256 signed, canonical base64url, expires after 30 days. Legacy permanent links are rejected. User existence/deletion and version are checked under a user row lock. Authenticated email preference updates acquire the lock before loading state and increment the user's version, revoking all old category links for that user; push-only changes do not. Deletion revokes links too. Logged-out unsubscribe remains available for JSON and RFC8058 mail-provider POSTs. POST /notifications/resubscribe is removed and no longer public. Re-enable only through authenticated preferences. Tests cover tampering, canonical encoding, expiry edges, removed endpoint, settings revocation and unchanged push preferences.

## Web Push

Every new notification also goes to the recipient's devices as a system notification (VAPID, RFC 8030/8291/8292), besides the bell and the e-mail. Each browser uses its own push service (Apple, FCM, Mozilla, Windows); there is no third-party SDK.

- **Subscriptions** (`PushController`, see [Push](api-notifications.md#push-pushcontroller-push)): the client posts `PushSubscription.toJSON()`; the owner comes from the token. Upsert by `endpoint`: a device where another account logs in moves to the caller. At most 10 per user; past it the subscription with the oldest `COALESCE(last_success_at, created_at)` is dropped (never the one just sent). Two simultaneous upserts of the same endpoint → one gets 409 from the unique constraint; the client resends when the app opens.
- **Anti-SSRF (`PushEndpointPolicy`):** the server POSTs to the URL the client sends, so the endpoint must be `https`, without credentials, on port 443 (or none), with a host that isn't an IP literal and is on the allowlist: `fcm.googleapis.com`, `android.googleapis.com`, `updates.push.services.mozilla.com`, or a subdomain of `.push.apple.com` / `.notify.windows.com` (the leading dot, so `push.apple.com.evil.com` fails). Otherwise 400 "Endpoint de notificação inválido". `p256dh` must decode (base64url) to a 65-byte uncompressed P-256 point (`0x04` first) and `auth` to 16 bytes, else 400 "Chaves de notificação inválidas". The sending `HttpClient` never follows redirects (connect 5 s, request 10 s).
- **When:** `NotificationType.pushable` (every type except `ADMIN_REVOKED`; `TEAMS_SORTED` and `ATTENDANCE_CONFIRMED_BY_ADMIN` are pushed though not e-mailed) and the recipient's push preference for the category (`pushEnabled`, else `NotificationCategory.defaultPush`, on in every category). Push and e-mail are independent channels.
- **Dispatch (`WebPushDispatcher`):** `NotificationDelivery` calls it after the commit; `@Async` on Boot's default virtual-thread executor, no pacing (push services have no quota like Resend's). One short read-only transaction with four queries whatever the batch (the rows with their references, the recipients' subscriptions, their preferences, a grouped unread count; the last two only for recipients with a device), then the sends outside it, one per device, and one write transaction with two bulk statements: `last_success_at` for the 2xx, delete for 404/410. 400/413 are logged as errors (a bug of ours), 429/5xx/timeouts as warnings; no retry. A failure never stops the other devices.
- **Message:** the encrypted payload is JSON `{title, body, url, tag, unreadCount}`: `title` and `body` from `NotificationContent` (the body cut at 180 characters with "…", never splitting an emoji), `url` = the CTA path + `?notificacao={id}` (the app marks it read on open: the service worker has no token), `tag` = `"{type}-{dailyId, else peladaId}"` (a collapsed `TEAMS_SORTED` / `SESSION_FINISHED` replaces the one on screen), `unreadCount` for the app badge. Headers: `TTL` 24 h (`SESSION_REMINDER` / `DIARISTA_WINDOW_OPEN`: until the session starts, at least 1 h), `Urgency: high` for Presença and `normal` for the rest, `Topic` = 24 bytes of the SHA-256 of the tag in base64url (32 characters, the header's limit; the tag itself can be longer). Nothing beyond what the bell shows goes in the payload; the push service only sees its size.
- **Revocation:** a password reset (`PasswordResetService`), a password change (`UserService.changePassword`) and the account deletion (`AccountDeletionService`) delete every subscription of the user in the same transaction, because they revoke the sessions; the device that changed its password subscribes again when the app opens.
- **Keys:** without `VAPID_PRIVATE_KEY` the sender is `NoopWebPushSender` and `GET /push/vapid-public-key` answers 204 (the client shows "unconfigured"). Generate the pair once with `npx web-push generate-vapid-keys` (the raw base64url format `WebPushConfig` reads; the private scalar is turned into a JCA `ECPrivateKey`) and store both as GitHub secrets. `WebPushConfig` checks at startup that the private key signs what the public one verifies. **Changing the pair invalidates every subscription** (the devices subscribe again when the app opens): don't rotate it without a reason.
- Metric `futspring.webpush.sent{result=ok|gone|failed}`, one per send.
